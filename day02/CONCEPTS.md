# 延伸知識：pathlib 為什麼取代了 os.walk

## `pathlib.Path` 對 `os.path`／`os.walk` 的實務優勢

舊寫法要這樣拼路徑：

```python
import os
p = os.path.join(base_dir, "sub", "file.txt")
```

`pathlib` 讓路徑本身是一個物件，可以用 `/` 運算子組合：

```python
from pathlib import Path
p = Path(base_dir) / "sub" / "file.txt"
```

差別不只是好看。`os.path.join` 用字串拼接，容易在不同作業系統上因為分隔符號（Windows 是 `\`、Linux/macOS 是 `/`）寫出只在自己機器上能跑的程式——這也是規格裡「不得硬編碼路徑分隔符」的原因。`Path` 物件在底層自動處理這件事，你不需要知道現在是哪個作業系統。

`os.walk()` 回傳的是 `(目錄, 子目錄列表, 檔案列表)` 的三元組，你得自己寫遞迴邏輯或迴圈去組合完整路徑；`Path.rglob("*.py")` 直接把「遞迴找符合條件的檔案」這件事變成一行。現在 AI 生成的 Python 檔案操作程式碎，十之八九會直接用 `pathlib`，`os.walk` 越來越像是舊程式碼裡才會看到的寫法——這也是為什麼規格明確禁止用它：這天要練的是現在實務上真正會用的工具。

## `glob()` 與 `rglob()` 差在哪

- `Path(d).glob("*.py")`：只找 `d` **這一層**符合的檔案，不進子目錄。
- `Path(d).rglob("*.py")`：**遞迴**進所有子目錄找。`r` 就是 recursive。

兩者都回傳一個 generator（產生器，邊找邊給結果，不會一次把全部結果塞進記憶體），這點在檔案數量很大的目錄下有實際差異——你可以邊找邊處理，不用等全部掃完。

## 排序穩定性：「大小相同時按路徑排序」為什麼要特別講

`sorted()` 在 Python 是穩定排序（stable sort），如果你只用 `key=lambda f: f.stat().st_size`，大小相同的檔案之間的相對順序會維持「原始出現順序」——但這個「原始出現順序」是 `rglob` 遍歷檔案系統的順序，**不是路徑字母順序**，而且不同作業系統、不同檔案系統上這個順序可能不同。這就是為什麼規格要求「同大小按路徑排序」：要用 `key=lambda f: (-f.stat().st_size, str(f))` 這種**明確的次要排序鍵**，讓輸出結果在任何機器上都一樣，這樣你的測試斷言才能寫死一個固定的期望順序,而不是碰運氣。

## 看 AI 生成的檔案搜尋工具時，可以檢查什麼

- 是不是還在用 `os.walk` 或字串拼路徑（舊習慣殘留）。
- 排序有沒有明確的 tie-breaker（相同大小時的次序）。
- 大目錄、空目錄、找不到符合檔案時，回傳的是空列表還是拋例外——這兩種行為對呼叫端的影響完全不同，AI 常常沒有一致的選擇，同一份程式裡有的地方回傳 `None`、有的地方回傳 `[]`。
