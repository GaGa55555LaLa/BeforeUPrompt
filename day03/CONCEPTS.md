# 延伸知識：設定檔驗證為什麼跟「解析成功」是兩件事

## `tomllib` 解析成功，不代表資料是對的

`tomllib.load()` 只保證這份檔案「語法上」是合法 TOML，回傳的是一個巢狀 `dict`。它完全不知道你期望 `samples` 應該是正整數、`coverage_threshold` 應該落在 0～1 之間——這些是**你的程式的business rule（業務規則）**，不是 TOML 格式本身的規則。這正是口頭驗收要問的：「為何解析成功仍需驗證？」——因為 parser 只負責「這是不是合法的 TOML 語法」，不負責「這個數字對我的程式有沒有意義」。一份寫著 `samples = -5` 的設定檔對 `tomllib` 來說完全合法。

## `true` 與 `"true"` 的差別，以及為什麼這件事值得寫進規格

TOML 有原生的布林型別，`save_raw_data = true`（不加引號）解析出來是 Python 的 `True`（`bool`）；`save_raw_data = "true"`（加引號）解析出來是字串 `"true"`。如果你的驗證邏輯寫成 `if config["save_raw_data"]:`，這兩種輸入都會被當成「真」——字串 `"true"` 是非空字串，在 Python 裡本身就是 truthy。**這代表型別錯誤有可能被 `if` 悄悄吞掉，不會馬上出錯，但語意已經不對了。** 這也是為什麼規格要求「save_raw_data 為布林值」要真的檢查 `isinstance(value, bool)`，而不是只看它能不能通過 `if`。

## 手動驗證 vs. `pydantic`：現在的 AI 工具會怎麼選

實務上，Python 生態圈處理「驗證設定/輸入資料」這件事，很常見的做法是用 `pydantic`（或 `dataclasses` + 手寫檢查）定義一個 schema（資料結構描述），一次宣告好每個欄位的型別與限制條件，函式庫自動幫你檢查、產生清楚的錯誤訊息。如果你現在直接叫 AI「幫我驗證這個 TOML 設定檔」，很大機率它會建議你用 `pydantic`。

這天故意要求你手寫驗證邏輯（一個一個 `if` 檢查），不是因為手寫比較好，而是因為：**你要先知道 `pydantic` 幫你做掉的是什麼，才能判斷它什麼時候會驗證不到你要的東西、或者錯誤訊息不夠清楚需要客製。** 如果你沒手寫過這段邏輯，看到 AI 生成的 `pydantic` model 時，你很難判斷它裡面的 `Field(gt=0, le=1)` 到底夠不夠——是不是漏了「非空字串」這種 `pydantic` 預設不會自動幫你檢查的規則。
