# 延伸知識：測試在驗證什麼，以及 AI 生成測試最常漏掉的東西

## 每個測試都在回答一個具體問題

好的測試名稱本身就是一個問題的答案，例如 `test_baseline_missing_raises_value_error` 直接講清楚「baseline 不存在時應該拋 ValueError」。寫測試前，先把「我要驗證的具體行為」用一句話講出來，再把它翻成程式碼——這個順序反過來（先寫程式碼，再隨便補幾個測試讓它變綠燈）是 AI 生成測試最常見的問題：**測試通過了，但沒人講得出這個測試在保護什麼。** 這正是這天口頭驗收要問的：「測試是在驗證外部行為，還是綁死內部實作？」

## 驗證外部行為 vs. 綁死內部實作

假設 `mean()` 內部原本用 `sum(values) / len(values)`，你把它改成用 `statistics.mean()`——如果測試寫的是「輸入 `[1,2,3]` 應該輸出 `2.0`」，這種測試在重構後應該還是通過，因為它驗證的是**外部行為**（給定輸入，輸出是什麼），不管內部怎麼實作。

但如果測試寫成「檢查函式內部呼叫了 `sum()` 這個 built-in 幾次」，這種測試綑死了實作細節，一旦你合理地重構內部寫法，測試就會失敗——即使外部行為完全沒變。**AI 生成的測試有時會過度依賴 mock/monkeypatch 去檢查「呼叫了什麼」而不是「回傳了什麼」，導致測試變成重構的阻礙，而不是重構的安全網。**

## 為什麼「必測案例」要包含這麼多種空/邊界輸入

正常案例只能證明「程式在期望的情況下能動」，證明不了「程式在意外情況下不會亂動」。這天列的必測案例（空檔、只有 header、單筆、負數、0、NaN、缺欄位……）背後都對應一種真實世界會發生的資料損壞方式：使用者存檔案時忘記存內容（空檔）、只複製了表頭範本（只有 header）、輸入時打錯符號、上游系統送出 `NaN` 或 `Infinity`。**如果你只測「正常輸入」，你測的其實是最不可能出錯的那個情況。**

## `pytest.raises` 跟 `tmp_path` 各自在保證什麼

- `with pytest.raises(ValueError): ...`：明確斷言「這段程式碼應該拋出這個例外」，而不是讓測試因為意外的例外而失敗——這兩者看起來像，但意義完全不同：前者是「我預期這裡會出錯，且必須是這種錯」，後者是「測試意外壞掉」。
- `tmp_path`：pytest 內建的 fixture（測試前自動準備好的資源），每次測試給你一個獨立的臨時目錄，測完自動清掉。用它模擬「讀寫真實檔案」的情境，同時保證測試之間不會互相污染彼此的檔案系統狀態——這是測試獨立性（test isolation）的具體實踐。

## 十幾個「必測案例」寫成十幾個函式，會發生什麼事

這天列的必測案例有十一種（正常、空檔、只有 header、單筆、負數、0、NaN、缺欄位、非數字、baseline 不存在、重複項、名稱含前後空白）。如果你老實地為每一種各寫一個 `test_xxx()` 函式，會發現大部分函式長得幾乎一樣：準備一份 CSV 內容、呼叫同一個函式、斷言同一種例外或同一種回傳值，唯一的差異只有輸入的資料跟預期結果。**這種「函式主體幾乎複製貼上，只有輸入/預期輸出不同」的重複，在真實測試套件裡幾乎一定會被改寫成 `pytest.mark.parametrize`：**

```python
import pytest

@pytest.mark.parametrize(
    "csv_text, expected_error",
    [
        ("store,item,price\n", None),                    # 只有 header，視為合法空結果
        ("store,item,price\nS01,rice,-1.0\n", ValueError), # 負數價格
        ("store,item,price\nS01,rice,nan\n", ValueError),  # NaN
        ("store,item,price\nS01,rice\n", ValueError),      # 缺欄位
    ],
)
def test_parse_rejects_invalid_rows(csv_text, expected_error):
    if expected_error is None:
        parse_prices(csv_text)  # 不應拋例外
    else:
        with pytest.raises(expected_error):
            parse_prices(csv_text)
```

一個 `@pytest.mark.parametrize` 裝飾的測試函式，會依你給的每一組參數各跑一次，`pytest -v` 的輸出裡每一組都會顯示成獨立的一行（例如 `test_parse_rejects_invalid_rows[csv_text0-expected_error0]`），**你不會因為合併成一個函式就看不出哪一組案例失敗了**。這解決了兩個實際問題：改動驗證邏輯時只要改一處（不用同步改十一個函式的斷言寫法），以及新增第十二種案例時只要多加一行參數、不用複製貼上整個函式骨架再修改。

**什麼時候不該硬套 parametrize**：如果十一種案例裡有幾種的**驗證方式**根本不同（例如有的要檢查拋出的例外訊息字串、有的要檢查回傳的 list 內容、有的要檢查有沒有寫 log），硬塞進同一個參數化測試會讓函式內部長出一堆 `if/else` 去分辨「這組參數該用哪種斷言」，這樣反而比十一個獨立函式更難讀。**parametrize 適合「驗證邏輯相同、只有輸入跟預期結果不同」的案例；驗證邏輯本身不同時，維持獨立函式，或者依驗證方式分成兩三組 parametrize，會比硬塞成一個更清楚。** 這天不強制要求用 parametrize（規格只要求案例都被覆蓋），但看到 AI 生成的測試檔案裡有十幾個幾乎一樣的函式時，值得想一下能不能用這個工具收斂。

## 名稱含前後空白這個案例，為什麼值得特別點名

`"S01"` 跟 `"S01 "`（結尾多一個空格）對電腦來說是不同字串，但對人來說是同一間商店。這種輸入很容易在真實資料裡出現（Excel 複製貼上、CSV 手動編輯常見），而且不會讓程式當掉——它會**安靜地產生兩個「不同」的商店分類**，讓報表看起來多了一間不存在的商店。這類錯誤最難抓，因為程式表面上完全正常執行、沒有拋任何例外，只是結果悄悄錯了。規格要求你明確選擇一種處理方式並寫下理由，就是逼你意識到「這裡有一個決定要做」，而不是讓它變成沒人注意到的隨機行為。
