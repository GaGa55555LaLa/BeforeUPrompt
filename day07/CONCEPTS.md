# 延伸知識：一份工具的 README/文件實務上該長怎樣

## `PROJECT_README.md` 不是「隨便寫寫交作業」，它模擬的是真實情境

當你（或別人）三個月後回頭要用這個工具，或者要把它交給另一個人維護，沒有人會想重新讀一次全部的程式碼。一份好的工具文件通常回答這幾個問題，順序大致就是讀者會依序想知道的：

1. **這是做什麼的**（一句話）。
2. **怎麼裝、怎麼跑**（環境需求、安裝指令、最小可執行範例）。
3. **輸入格式**（這裡是 TOML 欄位，包含每個欄位的型別與限制）。
4. **輸出格式與 exit code**——特別是 exit code，因為呼叫這個工具的人（或另一支腳本）需要知道怎麼判斷成功失敗。
5. **已知限制**：老實講「這個工具目前不處理什麼」，比不寫、讓人自己踩到地雷好得多。

這份文件的讀者預設是「沒讀過程式碼的人」，所以不用假設讀者知道你的內部函式怎麼設計。

## `--json` 這種輸出模式切換，實務上在解決什麼問題

同一份資訊，人類看的時候想要排版好看、有顏色、有空白對齊；另一支程式要讀的時候想要結構化、好 parse、不要有多餘的裝飾字元。`--json` 這種 flag 讓同一個工具同時服務兩種讀者：不加參數時輸出給人看的摘要，加了 `--json` 就輸出機器好解析的結構化資料。這是一個很常見的 CLI 設計模式——你會在 `docker`、`kubectl`、`gh`（GitHub CLI）這類工具上看到同樣的 `--json`/`--output=json` 慣例。

**這也是為什麼「非零 exit code」跟「輸出格式」要分開處理**：不管有沒有加 `--json`，失敗時的 exit code 都要一致，這樣呼叫端（可能是另一支腳本，也可能是 CI/CD pipeline）可以只看 exit code 判斷成敗，不需要去解析輸出內容的格式。

## 這天新增設定欄位，為什麼要問「修改哪些地方」

如果你的程式把「讀取」「驗證」「使用這個欄位」的邏輯分散在同一個函式裡，新增一個欄位可能要改五、六個地方，而且很容易漏掉其中一處（例如漏了驗證，或者漏了在 `--json` 輸出裡加上這個欄位）。如果結構夠清楚（驗證邏輯集中在一處、資料流是單向的），新增欄位理論上只需要改 1～2 個地方：驗證規則加一條、輸出時多帶一個欄位。**這天口頭驗收問的其實是在檢驗你的程式結構夠不夠「對修改友善」，這也是 `RUBRIC.md` 裡「可獨立完成並修改需求」這個判準的具體體現。**
