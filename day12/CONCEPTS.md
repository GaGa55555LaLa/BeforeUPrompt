# 延伸知識：故障注入是在系統性地找測試沒覆蓋到的角落

## 故障注入（fault injection）跟一般寫測試的心態差異

一般寫測試的心態常常是「我寫完功能了，順便補幾個測試」——這種心態下寫出來的測試，很自然會偏向「證明程式在我原本設計的使用情境下能動」。故障注入的心態反過來：**先假設系統一定會遇到各種故障或壞資料，主動去列出所有可能的破壞方式,再去驗證程式在每一種情況下的行為是不是「合理的失敗」而不是「未預期的崩潰」。**

這天列的必測案例（CSV 不存在、只有 header、重複項、coverage 恰好 50%……）不是隨便湊數，每一個都對應一種真實會發生的資料損壞或邊界情況。**「coverage 恰好等於門檻」特別值得注意**：邊界值（正好等於門檻,不是略高或略低）是最容易寫錯 `<` 跟 `<=` 的地方，這種 off-by-one（差一錯誤）在真實程式裡非常常見，而且測試如果只測「明顯高於門檻」跟「明顯低於門檻」,永遠不會抓到這種錯誤。

## 「錯誤指出原因，不只是被捕捉」在檢查什麼

一個測試斷言 `with pytest.raises(ValueError)` 只證明「這裡真的會拋錯」，但如果錯誤訊息是空的或者只寫「發生錯誤」，使用者（或你自己半年後）除錯時完全沒有線索。好的作法是同時斷言錯誤訊息包含關鍵資訊，例如：

```python
with pytest.raises(ValueError, match="baseline .* not found"):
    ...
```

這逼你在寫 `raise ValueError(...)` 的時候，就要放進「哪個 baseline」「為什麼找不到」這類具體資訊，而不是隨便丟一句通用訊息。**故障注入測試如果只驗證「有沒有拋錯」，跟只驗證「程式沒當掉」其實是同一個層次的偷懶——你要驗證的是「錯誤處理得夠不夠讓人看懂」。**

## `monkeypatch` 模擬 `PermissionError` 這種案例，為什麼值得特別處理

「輸出檔案時沒有寫入權限」這種錯誤，在你自己的開發機器上幾乎不會自然發生（你對自己的專案目錄通常有完整權限），但在其他環境（例如唯讀的容器、CI 環境、別人設定過權限的伺服器）完全可能發生。**你沒辦法可靠地在測試裡真的製造一個沒有寫入權限的目錄（不同作業系統的權限模型不一樣，行為也不保證一致）**，這正是 `monkeypatch` 派上用場的地方：直接讓 `open()` 或寫檔案的函式在被呼叫時「假裝」拋出 `PermissionError`，測試只驗證「拋出這個錯誤之後，我的程式有沒有妥善處理」，不需要真的重現造成這個錯誤的環境。

## 十幾種案例，別再每種都複製貼上一個函式

這天要求至少 14 個測試，如果每種故障案例都各寫一個獨立函式，你會發現大部分函式的骨架（準備壞資料 → 呼叫函式 → 斷言拋什麼錯）幾乎一樣，只有輸入跟預期錯誤不同。day06 的 [CONCEPTS.md](../day06/CONCEPTS.md) 那天已經講過用 `@pytest.mark.parametrize` 收斂這種重複——這天案例更多，重複也更明顯，是重新用一次那個工具的好機會。判斷原則一樣：**驗證邏輯（斷言的寫法）相同、只有輸入/預期結果不同的案例，適合合併；驗證邏輯本身不同（例如有的檢查例外訊息字串、有的檢查 log 輸出）的案例，維持獨立函式。**

## 這跟 property-based testing（基於性質的測試）的關係

這天寫的每個測試案例都是你手動想出來的「一個具體的壞輸入」。還有一種更進階的做法叫 property-based testing（Python 生態圈常用的函式庫是 `hypothesis`），做法不是你列出具體案例，而是你描述「輸入的性質」（例如「任何非空字串」「任何浮點數，包括負數跟極端值」），工具自動幫你生成大量隨機組合去測試，甚至會主動嘗試找出讓程式壞掉的邊界值組合，比你手動想到的案例更廣。這個訓練專案沒有用到 `hypothesis`（屬於第三方套件），但故障注入的思考方式——「系統性地假設會出錯，而不是只測我想到的案例」——跟 property-based testing 是同一個精神的兩種實踐方式，值得知道業界還有這條路可以走。
