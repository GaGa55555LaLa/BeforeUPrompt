# 延伸知識：什麼時候「手動操作 `sys.path`」是合理選擇，不是偷懶

`final_project/CONCEPTS.md` 已經講過 `sys.path` 是什麼、`python -m` 怎麼自動處理它、`ModuleNotFoundError` 通常代表什麼。那篇的立場比較保守：「看到 AI 建議塞 `sys.path.insert/append`，值得先問自己是不是該換成 `-m` 或安裝成套件」。這天要補的是另一半：**手動操作 `sys.path` 不是永遠錯的，只是要做得有意識、做得跟目前工作目錄無關**，而且要知道自己在真實世界裡什麼時候真的會需要它。

## 為什麼這天不能用 `python -m` 解決

final_project 能靠 `python -m price_report` 避開手動處理 `sys.path`，前提是 `price_report` 是一個正式的套件（有 `__init__.py`、有清楚的目錄結構）。但 `vendor/stringutils.py` 這種情境很常見：**一個沒有被包成套件、甚至可能是別人給你的一支獨立 `.py` 檔案，你想直接拿來用，但又不想（或不能）把它正式裝成一個套件**——這在快速原型開發、內部工具、限制網路存取無法 `pip install` 的環境、或者只是懶得幫一支小檔案寫完整的套件結構時,是真實會發生的情境。這時候 `-m` 幫不上忙，因為它解決的是「怎麼把一個**已經是套件**的東西的所在目錄加進 `sys.path`」，不是「怎麼把任意一個目錄加進 `sys.path`」。

## `sys.path.append(".")` 為什麼是反面案例：依賴目前工作目錄的路徑

`"."` 代表「目前工作目錄」，這個值**完全取決於你從哪裡執行這支程式**，跟這支程式檔案本身放在哪裡無關。如果你習慣從 `day15/` 這一層執行 `python solution.py`，`"."` 剛好就是 `day15/`，看起來能動；但只要換一個執行方式（例如寫一個排程腳本從別的目錄呼叫它、或者另一個人把整包程式移到別的地方執行），`"."` 指到的目錄完全不同，`import stringutils` 立刻失效——而且失敗的方式通常是 `ModuleNotFoundError`，錯誤訊息本身不會告訴你「因為你換了執行目錄」，除錯起來很花時間。

`Path(__file__).resolve().parent` 解決的正是這個問題：`__file__` 是「這支程式檔案自己的路徑」，跟執行時的工作目錄無關——**不管你從哪裡呼叫這支程式，`__file__` 指到的永遠是同一個實體檔案，`.resolve().parent` 算出來的 `vendor/` 路徑也永遠是同一個**。這是任何需要「相對於程式自己所在位置」找東西的程式碼都該用的寫法，跟這天測試要求「從跟 `day15/` 無關的目錄執行仍要能動」是同一件事的兩種講法。

## 為什麼要檢查重複、不能每次呼叫都無條件 `insert`

`sys.path` 是一個 list，`insert`／`append` 不會自動去重。如果一支程式在啟動流程裡（例如某個會被多次呼叫的函式，或者測試套件裡每個測試都呼叫一次）不檢查就無條件塞路徑，`sys.path` 裡會越塞越多份完全相同的路徑——**不會讓程式壞掉（Python 找模組時找到第一個符合的就停了，不會因為後面有重複而出錯），但這是一種會隨著執行次數累積、卻永遠不會被清掉的隱性狀態**，long-running 的程式（例如一個常駐服務、或者互動式的 REPL/notebook）如果反覆執行到這段程式碼，`sys.path` 可能累積到很長，讓每一次 `import` 找不到的模組要花更久才能確認真的找不到（Python 要把 `sys.path` 裡每個目錄都找過一輪才會放棄）。加一個 `if vendor_str not in sys.path:` 這種檢查，成本很低，換來的是「這個操作可以放心重複呼叫」的保證。

## 真實世界裡，手動操作 `sys.path` 常見出現在哪些情境

- **Jupyter Notebook／互動式分析腳本**：常見在 notebook 開頭看到 `sys.path.append("../src")`，因為 notebook 通常不會被正式包成套件，只是想暫時拉進同一個 repo 裡另一個資料夾的程式碼。
- **Plugin／外掛系統**：工具在執行時掃描一個使用者指定的目錄（例如 `~/.myapp/plugins/`），把它動態加進 `sys.path` 後才 `import` 使用者自己寫的外掛模組——這種情境下要匯入的模組根本不存在於這支程式自己的原始碼裡，沒辦法透過套件安裝解決，因為使用者可能在你發行這支工具之後才寫外掛。
- **測試檔案裡臨時匯入待測程式碼**：某些專案的測試檔案會在最上面手動調整 `sys.path`，讓測試檔案能匯到還沒被安裝、只是躺在原始碼目錄裡的模組——這其實通常代表專案設定（例如 `pyproject.toml` 或 `pytest.ini` 裡的 `pythonpath`／`rootdir` 設定）沒配好，是可以透過設定解決、但很多專案就是先用 `sys.path` 湊合著跑。
- **限制網路存取的環境**：某些企業內部或離線環境沒辦法 `pip install` 任意套件，只能把需要的程式碼整份複製進自己的 repo（業界俗稱 vendoring），再手動處理匯入路徑。

## `PYTHONPATH` 環境變數：不改程式碼版的做法

如果你不想在程式碼裡寫任何 `sys.path` 操作，另一個做法是執行前設定環境變數：

```bash
PYTHONPATH=day15/vendor python day15/solution.py "S01"
```

效果跟程式碼裡 `sys.path.insert()` 類似（`PYTHONPATH` 裡列的目錄會被加進 `sys.path`），差別是**這個設定跟著「怎麼執行」走，不是跟著「程式碼本身」走**——換一台機器、換一個沒設這個環境變數的執行環境，程式就會壞掉，而且失敗時完全看不出程式碼哪裡有問題（因為程式碼本身沒錯，是外部環境少了一個變數）。這也是為什麼這天要求的是程式碼裡自己算出正確路徑，而不是依賴外部環境變數——**能自己保證正確性的程式，比依賴外部設定才能正確的程式更可靠**，`PYTHONPATH` 更適合用在暫時除錯、或者 CI 設定檔這種本來就會明確記錄執行環境的地方。

## AI 生成程式碼裡常見的 `sys.path` 地雷

問 AI「這支程式匯入不到模組怎麼辦」，很常見會直接拿到一行 `sys.path.append("../../其他資料夾")` 貼在檔案最上面——這種相對路徑寫法**同時踩了兩個問題**：一是跟目前工作目錄有關（跟這天要避開的 `sys.path.append(".")` 問題一樣），二是 `../../` 這種寫法假設了「這支程式檔案跟目標模組之間的相對層級關係」，一旦有人把任何一邊的資料夾搬動位置，這行程式碼就會指向錯誤的地方而不會有任何警告——它不會報錯,只會安靜地 import 到別的東西,或者找不到而 crash,但錯誤訊息完全不會提示「因為目錄結構被搬動過」。看到這種寫法，值得先問「這個路徑是相對於哪裡算的」，如果答案是「相對於執行時的工作目錄」而不是「相對於這支檔案自己的位置」，這通常就是之後會出問題的地方。
